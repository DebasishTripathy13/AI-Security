Securing agents, multi-agent systems and MCP

Designing agents that stay safe even when the model is hijacked. Covers the lethal trifecta, the Rule of Two, a secure agent reference architecture, identity, HITL, sandboxing, injection-resistant design patterns, multi-agent trust, and MCP/A2A attacks with real incidents.

⏱ 45 minPriority ★★★★
Key takeaways
  • Lethal trifecta / Rule of Two: never combine untrusted input, sensitive access and external actions in one session without a human.
  • The LLM proposes and deterministic code decides: tool gateway + policy engine + user-scoped (OBO) identity + sandbox.
  • Injection-resistant patterns: plan-then-execute, dual LLM, CaMeL-style capability tracking.
  • MCP risks: tool poisoning, rug pulls, shadowing, token passthrough, local server RCE. Mitigate with a registry, pinning, hashing, OAuth and a gateway.

What an agent is

Components

  • Model: reasons and plans
  • Tools: functions, APIs, MCP servers, browser, code
  • Memory: short-term context, long-term store
  • Planner/loop: ReAct, plan-and-execute, reflection
  • Identity: whose permissions it uses

Autonomy spectrum

  • Assistant: suggests; a human acts
  • Copilot: acts with per-action approval
  • Supervised autonomous: acts; a human approves high-risk steps
  • Fully autonomous: acts alone (background agents)

Risk grows with autonomy × privilege × exposure to untrusted input.

Agent types you'll hear about

  • Coding agents (Claude Code, Copilot agent, Cursor)
  • Computer-use / browser agents
  • Enterprise workflow agents (Copilot Studio, Agentforce)
  • Multi-agent frameworks (AutoGen, CrewAI, LangGraph, Semantic Kernel)

The lethal trifecta and the Rule of Two

Lethal trifecta (Simon Willison, June 2025): if an agent combines

  1. access to private data,
  2. exposure to untrusted content (anything an attacker can write), and
  3. a way to communicate externally (HTTP, email, image URLs, links, PR comments),

then a prompt injection can steal the data. Remove any one leg and exfiltration becomes much harder.

Meta's "Agents Rule of Two" (Oct 2025) generalizes this. Until injection is reliably solved, an agent session should have at most two of:

  • [A] processes untrustworthy inputs
  • [B] has access to sensitive systems or private data
  • [C] can change state or communicate externally

If a task needs all three, add human approval or split it into separate sessions or agents.

Identity and authorization for agents

Principles

  • Agents are non-human identities. Give each one its own managed identity with an owner (e.g. Microsoft Entra Agent ID; workload identities; SPIFFE/SPIRE for services).
  • When acting for a user, use delegated access: OAuth 2.0 on-behalf-of / token exchange (RFC 8693). The effective permission is the intersection of user and agent rights.
  • Tokens are short-lived, least-scope, audience-bound (one token per downstream API).
  • Never put credentials in the prompt, memory or logs. The gateway injects them at call time.
  • Authorize at execution time, not just at plan time (TOCTOU).
  • Step-up auth (re-auth or MFA) for sensitive actions.

Anti-patterns to call out

  • One "god" service account shared by all agents and users
  • A long-lived PAT with access to all repos given to a coding agent
  • Database admin connection string for a text-to-SQL bot
  • Token passthrough: an MCP server forwarding the client's token to other APIs (forbidden by the MCP spec)
  • Agent-to-agent delegation that loses the original user's identity, so a low-privilege user gets a high-privilege agent's rights
  • Using the LLM to decide "is this user allowed?"

Approval fatigueIf you ask humans to approve everything, they approve everything (OWASP T10 "Overwhelming HITL", ASI09). Tier the actions, batch low-risk items, show what will happen rather than the agent's persuasive summary, and measure approval rates. A 99.9% approval rate means the control isn't doing anything.

Sandboxing and code execution

  • Isolation strength: process < container < gVisor (user-space kernel) < Firecracker/Kata microVM < separate VM/host. WASM is good for constrained plugins.
  • Ephemeral: a fresh environment per task; destroy afterwards; nothing persists.
  • No network by default; if needed, go through an egress proxy with an allowlist.
  • No secrets or cloud credentials in the sandbox (block the metadata endpoint).
  • Read-only base FS, non-root user, seccomp/AppArmor, CPU/memory/time limits.
  • Protect files that auto-execute (MCP configs, git hooks, .bashrc, CI files, IDE settings). Coding agents have been exploited by writing to them.

Memory security

Threats

  • Injected "remember that…" instructions persist (ChatGPT "SpAIware", 2024)
  • Delayed triggers ("when the user says 'yes', save X")
  • Shared memory leaks across users or tenants
  • Summaries that preserve injected instructions

Controls

  • Partition memory per user, tenant and agent
  • Provenance on every entry; untrusted sources can't write long-term memory
  • Review or confirm memory writes; show users what's remembered
  • TTL, versioning, rollback; scan memory for imperative instructions

Design patterns that resist prompt injection

From "Design Patterns for Securing LLM Agents against Prompt Injections" (Beurer-Kellner et al., 2025, with authors from IBM, Invariant Labs, ETH Zurich, Google and Microsoft). The idea is to constrain what untrusted data can influence instead of hoping the model resists it.

PatternHow it worksTrade-off
Action-SelectorThe LLM only maps the request to one of a fixed set of actions; tool outputs are never fed back to itVery safe; limited flexibility
Plan-Then-ExecuteThe LLM fixes the plan (sequence of tool calls) before seeing untrusted data; data can't add new actionsInjection can still corrupt arguments within the plan
LLM Map-ReduceIsolated sub-agents each process one untrusted item and return constrained results (e.g. boolean); an aggregator combines themGood for batch processing
Dual LLMA privileged LLM plans and calls tools but never sees untrusted text; a quarantined LLM processes untrusted text with no tools, and results are passed as opaque variablesComplexity; data flows still need policies
Code-Then-ExecuteThe LLM writes a program for the task (e.g. in a restricted DSL), which runs in an interpreter that tracks data provenance. This is the CaMeL approachStrongest guarantees; engineering effort; lower task success
Context-MinimizationRemove the user's original prompt or unnecessary content from context after use so injected content can't build on itSimple; partial protection
Model-level defenses (useful, not sufficient)Instruction hierarchy training (OpenAI, 2024): models learn to prioritize system > developer > user > tool content. Spotlighting (Microsoft, 2024): delimiting, datamarking or encoding untrusted text. Prompt-injection classifiers: Azure Prompt Shields, Meta Prompt Guard, Lakera. Combine them with the architectural patterns above.

Multi-agent systems

Multi-agent threats

  • Agent-to-agent prompt injection: a compromised or browsing agent passes instructions upstream
  • Impersonation and spoofing of agents or Agent Cards
  • Privilege escalation via delegation: low-privilege agent asks high-privilege agent
  • Trust transitivity: A trusts B, B trusts C, so A ends up trusting C
  • Cascading failures and hallucination amplification
  • Collusion and emergent behavior; infinite delegation loops
  • Repudiation: no trace across agents

Controls

  • Zero trust between agents: authenticate (mTLS / signed JWTs), authorize each request
  • Least privilege per agent; separate identities; no shared credentials
  • Typed, schema-validated messages; no "instructions" field from untrusted peers
  • Propagate user identity and data provenance (taint) through the chain
  • Verifier/critic agent or deterministic checks before high-impact actions
  • Max delegation depth, quotas, circuit breakers
  • Distributed tracing (OpenTelemetry GenAI conventions) and an agent registry
Microsoft's agentic failure-mode taxonomy (Apr 2025)Microsoft's AI Red Team split failures into novel and existing modes, each with security and safety variants. Novel security failures include agent compromise, agent injection, agent impersonation, agent flow manipulation and multi-agent jailbreaks. Existing risks that agents amplify include memory poisoning, cross-domain prompt injection, human-in-the-loop bypass, incorrect permissions, excessive agency and resource exhaustion. Its case study showed an email agent's memory being poisoned by a single crafted email, after which it forwarded internal mail to an attacker. See module 12.

MCP (Model Context Protocol) security

MCP in one minute

  • An open protocol (introduced by Anthropic in Nov 2024, now governed under the Linux Foundation's Agentic AI Foundation) that standardizes how AI hosts (IDEs, desktop apps, agents) connect to servers that expose capabilities.
  • Server primitives: tools (functions the model can call), resources (data/context), prompts (templates). Client primitives: sampling (server asks the host's LLM), roots, elicitation (server asks the user).
  • Transports: stdio (local subprocess) and Streamable HTTP (remote).
  • Authorization for HTTP servers is OAuth 2.1-based. MCP servers are OAuth resource servers, publish Protected Resource Metadata (RFC 9728), clients use resource indicators (RFC 8707) and PKCE, and token passthrough is forbidden.
  • The security catch: tool descriptions are text that goes straight into the model's context, and local servers run with the user's privileges.

MCP hardening checklist

  • Maintain an allowlist/registry of approved MCP servers; block unknown ones (enterprise policy)
  • Install from trusted sources; pin versions; verify signatures/hashes; watch for typosquats
  • Hash tool definitions at approval; alert and re-approve on change (anti-rug-pull)
  • Read the full tool descriptions; scan for instructions and invisible characters
  • Run local servers in containers/sandboxes with minimal filesystem and network access
  • Remote servers: OAuth 2.1 per spec, PKCE, audience-bound tokens, no token passthrough
  • Least-privilege tokens per server; never admin/service-role keys
  • Separate untrusted-content servers (web, issues, email) from sensitive-data servers, or require HITL across them
  • Human confirmation for sensitive tools; disable "auto-approve all"
  • Route through an MCP gateway/proxy for policy, logging and DLP
  • Log every tool invocation with server, tool, args and result size

A2A (Agent2Agent) protocol security

  • What: an open protocol for agents to discover and collaborate with each other (Google, Apr 2025; now under the Linux Foundation). Agents publish an Agent Card (JSON at a well-known URL) describing skills, endpoint and supported auth schemes. Communication uses JSON-RPC over HTTPS with tasks, messages and artifacts, plus streaming and push notifications.
  • MCP vs A2A: MCP connects an agent to tools and data (vertical). A2A connects agents to agents (horizontal).
  • Risks: Agent Card spoofing or capability over-claiming; malicious remote agents injecting instructions into multi-turn sessions ("session smuggling"); push-notification webhooks abused for SSRF; weak auth between agents; sensitive data shared with third-party agents; replay.
  • Controls: verify Agent Card provenance (signed cards, domain verification, allowlist); strong auth (OAuth2/OIDC, mTLS); validate webhook URLs; treat remote agent output as untrusted; data-sharing policies; logging of cross-agent tasks.

Computer-use and coding agents

Computer-use / browser agents

  • Any text on screen is a prompt: web pages, pop-ups, ads, PDFs
  • ClickFix-style lures trick agents into running commands
  • Logged-in sessions give the agent the user's full web identity
  • Controls: dedicated VM/browser profile, no sensitive logged-in sessions, domain allowlists, HITL for logins, purchases and downloads, takeover mode, screenshot logging

Coding agents

  • Injection via READMEs, issues, code comments, dependencies, rules files
  • Auto-run ("YOLO") modes execute commands without review
  • Writes to auto-executing config (MCP config, hooks) → RCE (CurXecute)
  • Local AI CLIs abused by malware: the Nx "s1ngularity" supply-chain attack (Aug 2025) invoked installed AI CLIs with permissive flags to hunt for secrets
  • Controls: dev containers, no prod credentials, command allowlists, review diffs, protect config files, branch protection, scoped CI secrets

Detecting agent attacks

Log these

  • User, agent identity, on-behalf-of chain, session/trace ID
  • Prompts and context sources (doc IDs, URLs) with redaction
  • Every tool call: tool, server, arguments, result size, latency
  • Policy decisions (allow/deny/escalate) and human approvals
  • Memory writes; model and prompt versions

Detections

  • Injection-classifier hits followed by tool calls
  • Sensitive-read → external-send sequences in one session
  • First-seen egress domains; data in URL parameters
  • Spikes in tokens, spend, tool calls or delegation depth
  • Repeated policy denials (probing); memory writes with imperative text
  • Tool definition hash changes; new MCP servers
