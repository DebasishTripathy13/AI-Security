AI security foundations

The mental models behind every other module: how LLM applications work, why they're hard to secure, the full attack catalog, how to threat model, and what defense in depth looks like.

⏱ 30 minPriority ★★★
Key takeaways
  • AI security covers three things: security of AI (the focus of most roles), AI for security, and safety / responsible AI.
  • Prompt injection exists because instructions and data share one token stream. There's no equivalent of parameterized queries.
  • Be able to draw the reference architecture: authorization lives in the orchestrator and tool gateway, never in the LLM.
  • Know every attack class in two sentences: injection, jailbreak, exfiltration, poisoning, backdoors, evasion, extraction, inversion, membership inference, supply chain.
  • Defense in depth: deterministic layers (identity, action controls) for guarantees; probabilistic layers (classifiers) to reduce risk.

What "AI security" covers

Interviewers often open with "What is AI security?" A strong answer separates three related things:

Security of AI

Protecting AI systems (models, data, prompts, agents, pipelines) from attack. Covers prompt injection, poisoning, model theft and data leakage. This is the focus of most AI security roles.

AI for security

Using AI to defend: SOC copilots (e.g. Microsoft Security Copilot), malware classification, phishing detection, AI-assisted code review.

Safety & responsible AI

Preventing harmful outputs and outcomes: toxicity, bias, misinformation, dangerous capabilities. It overlaps with security, because a jailbreak is a security failure that causes a safety harm.

The systems you'll be asked about include chatbots, copilots, RAG assistants, tool-using agents, multi-agent systems, coding agents, computer-use/browser agents, and classic predictive ML (fraud models, malware classifiers, face recognition). Predictive ML is where evasion, poisoning and extraction research began.

How an LLM application actually works

The core mechanics

  • Tokens: text is split into sub-word tokens. The model predicts the next token, one at a time.
  • Context window: everything the model "sees" per call (system prompt, chat history, retrieved docs, tool results). It's a single token sequence.
  • Roles: system/developer, user, assistant and tool messages. They're a training convention, not an enforced privilege boundary.
  • Sampling: temperature and top-p control randomness, so the same input can produce different outputs. This makes testing statistical.
  • Stateless: the model has no memory. The app re-sends history each call or stores "memory" itself.

What makes it an application

  • Function / tool calling: the model emits structured JSON naming a tool and arguments. Your code executes it.
  • Embeddings: vectors that capture meaning, used for semantic search in RAG.
  • Orchestration: frameworks (LangChain, LangGraph, Semantic Kernel, AutoGen, CrewAI, OpenAI Agents SDK, Claude Agent SDK) assemble prompts, call tools and manage state.
  • Guardrails: classifiers and policies on input and output (Azure AI Content Safety, Llama Guard, NeMo Guardrails).

Prompt injection in more depth

Delivery vectors

  • Direct: chat box, API parameter, file name, form field
  • Indirect: web pages (browsing agents), emails/calendar invites (assistants), documents and RAG chunks, code comments/READMEs/issues (coding agents), tool or MCP responses and tool descriptions, images/audio (multimodal), other agents' messages
  • Stored / persistent: written into memory or a knowledge base, so it fires later for other users (stored-XSS-like)
  • Delayed / triggered: fires only when the user later says a trigger word (Gemini memory research, 2025)

Attacker goals

  • Data exfiltration (chat history, documents, secrets)
  • Unauthorized actions (send email, transfer money, change code)
  • Content manipulation (biased summaries, phishing links, fake citations)
  • Persistence (memory poisoning) and propagation (AI worms like Morris II, 2024)
  • Denial of service (refusals, loops)
  • Reputational harm (screenshot-able bad output)

GotchaPrompt injection and jailbreaking aren't the same thing. Jailbreaking targets the model's safety training to get prohibited content. Prompt injection targets the application by overriding the developer's instructions to make it do something unintended. OWASP files jailbreaking under LLM01 as a form of prompt injection.

NIST adversarial ML taxonomy (AI 100-2)

NIST AI 100-2 (Adversarial Machine Learning: A Taxonomy and Terminology, updated E2025) is the standard vocabulary. It classifies attacks by system type, lifecycle stage, attacker goals, capabilities and knowledge.

Predictive AI (PredAI)

  • Evasion: adversarial examples at deployment
  • Poisoning: availability, targeted, backdoor and model poisoning
  • Privacy: data reconstruction, membership inference, property inference, model extraction

Generative AI (GenAI)

  • All the above, plus:
  • Supply chain attacks
  • Direct prompt injection (incl. jailbreaks)
  • Indirect prompt injection
  • Misuse enablement: circumventing restrictions to produce harmful output
DimensionValues
Attacker goalsAvailability breakdown · Integrity violation · Privacy compromise · (GenAI) Misuse enablement
Attacker knowledgeWhite-box (full model access) · Gray-box (partial: architecture or data) · Black-box (query access only)
Attacker capabilitiesTraining data control, model control, testing data control, label limits, source code control, query access, resource control (for indirect injection)

Questions to ask in any AI threat model

  • What's the worst thing this system can do, not just say?
  • Where does untrusted content enter the context window (users, docs, web, email, tools, memory, other agents)?
  • Whose identity does the model act with: the user's, a service account, or its own?
  • Are authorization decisions made by deterministic code or by the LLM?
  • Can the system send data out (links, images, email, HTTP, tool calls)? That's the exfiltration path.
  • Which actions are irreversible, and do they need human approval?
  • Where did the model, datasets, adapters, plugins and MCP servers come from? Are they pinned and verified?
  • What persists (memory, KB, caches), and can untrusted input write to it?
  • What do we log, how is PII handled in logs, and can we reconstruct an incident?
  • How would we detect abuse, and how fast can we turn it off (kill switch)?

Other threat-modeling frameworks to name-drop: CSA MAESTRO (7-layer agentic threat modeling), Microsoft's "Threat Modeling AI/ML Systems and Dependencies" guidance, OWASP Threat Modeling, PASTA, LINDDUN (privacy). See module 13.

Defense in depth for AI systems

No single control stops prompt injection or jailbreaks. Stack them so that each layer catches what the previous one missed, and make the action layers deterministic.

1 · GovernanceAI inventory, risk assessment, acceptable use policy, ownership, NIST AI RMF / ISO 42001, vendor review
2 · Identity & accessUser authN, per-agent identities, OAuth on-behalf-of, short-lived scoped tokens, permission-aware retrieval
3 · Input controlsPrompt-attack classifiers (Prompt Shields, Prompt Guard), normalization, size limits, spotlighting of untrusted content
4 · Model layerSafety-aligned model, instruction hierarchy, hardened system prompt (no secrets), fine-tuning, temperature limits
5 · Output controlsContent safety filters, PII/DLP, groundedness checks, schema validation, encoding, link/image restrictions
6 · Action controlsTool allowlists, parameter validation, policy engine, HITL for high-risk actions, sandboxed execution, egress allowlists
7 · Monitoring & responseTelemetry, anomaly detection, abuse monitoring, AI incident response playbooks, kill switches, rollback
8 · AssuranceContinuous red teaming (PyRIT, garak), adversarial evals in CI, metrics (ASR), periodic third-party review
The key design insightLayers 3–5 are probabilistic: classifiers can be bypassed. Layers 2 and 6 are deterministic: code enforces them regardless of what the model says. Strong designs put the hard security guarantees in deterministic layers and use probabilistic layers to reduce noise and catch obvious abuse.

Glossary: adversarial ML terms

FGSMFast Gradient Sign Method (Goodfellow et al. 2014). One-step perturbation in the direction of the loss gradient's sign.
PGDProjected Gradient Descent (Madry et al. 2017). Iterative FGSM; the standard for adversarial training.
C&WCarlini & Wagner attack. An optimization-based, minimal-perturbation evasion attack.
GCGGreedy Coordinate Gradient (Zou et al. 2023). Optimizes an adversarial suffix that jailbreaks LLMs and transfers across models.
PAIR / TAPAttacker-LLM-driven jailbreak search. PAIR refines a prompt iteratively; TAP (Tree of Attacks with Pruning) branches and prunes.
CrescendoMulti-turn jailbreak (Russinovich et al., Microsoft 2024) that escalates gradually from benign questions.
Skeleton KeyMicrosoft-disclosed jailbreak (2024) that asks the model to augment its guidelines ("add a warning instead of refusing").
Many-shot jailbreakingAnthropic 2024. Fills a long context with many faux dialogues of compliance so the model follows the pattern.
TransferabilityAdversarial inputs crafted on one model often work on others, which enables black-box attacks via surrogate models.
Differential privacyA mathematical guarantee that limits how much any single record affects the model (DP-SGD).
